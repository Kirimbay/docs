## Что выполнить на сервере

Под root, на каждой машине с Hiddify Manager. Пользователям **ничего менять не нужно**.

```bash
rm -f /tmp/hiddify-block-torrents.sh
curl -fsSL -H 'Cache-Control: no-cache' \
  "https://raw.githubusercontent.com/Kirimbay/docs/cursor/hiddify-block-torrents-0aec/scripts/hiddify-block-torrents.sh?$(date +%s)" \
  -o /tmp/hiddify-block-torrents.sh
grep -m1 '^VERSION=' /tmp/hiddify-block-torrents.sh   # must be 1.6.6
sudo bash /tmp/hiddify-block-torrents.sh
hiddify-block-torrents doctor
```

`VERSION` должна быть **1.6.5** или новее. В `doctor` нужны **`kernel: OUTPUT allowlist ON`**, **`vpn-safe: OK`** и **`selftest: OK`**. Если `selftest: FAIL` и `:51413=rst` — пакеты с VPS всё ещё уходят, блок не в ядре.

**1.6.4** ложно откатывала фаервол: Hiddify INPUT режет SYN на тестовый veth, даже когда наших правил нет (`doctor` после отката всё равно `inbound SYN-ACK=timeout`). 1.6.5 открывает INPUT только для теста, сначала снимает baseline, и откатывает OUTPUT только если SYN-ACK умер *после* наших правил.

**1.6.2** роняла входящий VLESS/gRPC/Reality: финальный `drop` резал SYN-ACK клиенту, без `ipv6-icmp` ломался NDP. Если клиент «подключён», а все серверы `n/a` — сначала снимите фаервол:

```bash
sudo hiddify-block-torrents uninstall
# или, если команды нет:
nft delete table inet hiddify_notorrent
iptables -D OUTPUT -j HIDDIFY_NOTORRENT
ip6tables -D OUTPUT -j HIDDIFY_NOTORRENT
```

Потом ставьте **1.6.5** (curl с `?$(date +%s)`, `grep VERSION` должен показать 1.6.5).

Снять блок:

```bash
sudo hiddify-block-torrents uninstall
```

## Почему абуза приходит на IP сервера

Хостер видит пира с **вашего** адреса. Значит торрент вышел через VPS. Это не лечится настройками qBittorrent у клиента и не лечится «отсортируйте Users по гигабайтам».

Та же задача у других держателей панелей:

- [Hiddify #4712](https://github.com/hiddify/Hiddify-Manager/issues/4712) — просят универсальный блок BT из‑за DMCA. Ответ панели: «не скоро», совет «используйте DNS» (DNS пиров не закрывает).
- [XTLS/Xray #2300](https://github.com/XTLS/Xray-core/issues/2300), [3x-ui #3251](https://github.com/MHSanaei/3x-ui/issues/3251) — правило `protocol: bittorrent` ловит только незашифрованный handshake. qBittorrent с MSE/PE сниффер не видит.
- [kutovoys/xray-torrent-blocker](https://github.com/kutovoys/xray-torrent-blocker) — банит по access-логу. Если сниффер молчит, банить некого, абуза уходит.

Сниффер и порты 6881–6889 (то, что предложил хостер) для современного клиента недостаточны.

## Что делает 1.6.5 на сервере

1. **Ядро (главное).** nftables/iptables на **OUTPUT**. Случайные порты DHT/пира — drop. **80/443 не дыра:** SYN пускаем, первый payload обязан быть TLS (`16 03`) или HTTP (`GET `/`POST `/…). Пир qBittorrent на 443 (не TLS) отрезается. UDP/443 тоже не в allowlist — через него часто идёт BT ([Xray #4554](https://github.com/XTLS/Xray-core/pull/4554)). Пользователь ничего не включает.
2. **Нельзя повторить 1.6.2.** Drop только `NEW`, не UNTRACKED. SYN-ACK проверяется через veth **после** дырки в INPUT и baseline; откат только если ответ умер из‑за наших OUTPUT.
3. **Xray / sing-box** — allowlist портов и `bittorrent → blackhole`, как раньше. `hiddify-core` на сервере — это и есть sing-box (`hiddify-singbox.service`).
4. Подписи handshake/DHT и ipset трекеров — дополнительно, на них одних рассчитывать нельзя.

SSH **на** сервер не трогается (это INPUT). Исходящий SSH с машины на порт 22 тоже разрешён. Instagram / YouTube / Telegram / сайты остаются. Могут отвалиться игры и голосовой Discord через VPN.

Если на **той же** VPS крутится что-то своё на нестандартном исходящем порту (бэкап на :9000, свой VPN на :51820) — либо перенесите, либо напишите, добавим порт в allowlist.

## Как проверять именно абузу, а не «торрент на своём ПК»

Тест «скачал qBittorrent, ничего не настроил, включил Hiddify как системный прокси» часто **не попадает на VPS**: Windows не кормит клиент системным прокси, качает с домашнего IP. Хостер такой трафик с сервера не увидит.

Реальные пользователи в режиме **VPN/TUN** (Hiddify Next «всё через прокси», телефон, и т.п.) выходят с IP VPS. Их режет OUTPUT allowlist — без галочек в клиенте.

`doctor` после 1.5.0:

- `kernel: OUTPUT allowlist ON` — ядро режет;
- `catch-all: blocked_torrent` — Xray тоже режет;
- `peers: 0` во время *вашего* теста с системным прокси — этот тест на сервер не пришёл.

## Happ: маршрутизация в подписке

Клиенты **Happ** раз в час тянут подписку. По [доке Happ](https://docs.happ.info/main/dev-docs/routing) в тело (`/sub`, `/all.txt`) и в HTTP-заголовок `routing` кладётся

`happ://routing/onadd/{base64 JSON}`.

1.6.6 вшивает это в `hiddifypanel/panel/user/user.py` (функции `add_headers` и `links_imp`). После `install` перезапускается `hiddify-panel`. В профиле `BlockSites` — публичные трекеры/DHT bootstrap. `GlobalProxy=true`, Instagram/YouTube по-прежнему через VPN.

Это **не замена ядра**:

- работает только в Happ, не в Hiddify Next / v2rayNG;
- Happ режет **домены**, не порты — DHT и пиры на 443 до VPS всё равно дойдут;
- на обычной (не JSON) подписке пользователь может выключить routing в приложении.

Проверка: `hiddify-block-torrents status` → строка `happ: routing вшит`.

## VLESS

Входящий VLESS не меняется. Блок — после расшифровки и на OUTPUT уже расшифрованного исходящего.

На время установки ядра перезапускаются на секунды.
